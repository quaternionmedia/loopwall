**CLI demo v2 (2026-07-16):** `loopwall demo` now starts a capture, the Tier 0 monitor display, *and* a live-preview window together, in one command. Three real bugs surfaced building this, each with a permanent fix, not a workaround:

1. **Two processes can't open the same camera.** Confirmed empirically (a second `ffmpeg -f dshow` open on this dev machine's camera fails with an I/O error) before designing around it, not assumed. Live preview instead shares the ring's *one* capture process via FFmpeg's `tee` muxer — one encode, two sinks: the ring (unchanged) and `udp://127.0.0.1:<port>` as MPEG-TS, read by a persistent `ffplay`. `RingCapture` gained an optional `preview_udp_port` param, fully backward-compatible (all prior tests still pass unmodified).
2. **The tee muxer's bracketed option syntax breaks on Windows absolute paths** — `:` is tee's own option separator, colliding with a drive letter (`C:\...`); backslashes got silently mangled too. Root-caused with a minimal repro (confirmed: 0 ring segments, `[tee] No option found near "Users..."` in ffmpeg's own log once stderr wasn't suppressed) before fixing it — not patched blind. Fix: run ffmpeg with `cwd` set to the ring directory and use bare relative filenames inside the tee spec, sidestepping the escaping problem entirely rather than fighting tee's escaping rules.
3. **`lavfi` synthetic sources aren't real-time-paced by default** — ffmpeg processes them as fast as the CPU allows, so a test `RingCapture` reading "15s of content after a 4s sleep" is possible and did happen. Fixed with `-re` on the lavfi input (`monitor/camera.py`); existing lavfi-based tests' literal command-string assertions updated to match.

A fourth finding, caught before it became a bug rather than after: `ffplay.exe` on this machine is *also* a Chocolatey shim (confirmed by identical file size to `ffmpeg.exe`, 392704 bytes) — the same orphaned-child risk from the capture POC applies to the live-preview process too. Factored the process-tree-kill logic out of `RingCapture.stop()` into a shared `src/loopwall/proctree.py` (`kill_tree()`), used by both `RingCapture` and `demo.py`'s preview-process teardown, rather than duplicating or half-covering it. Two design problems, resolved rather than assumed away:

1. **Bar/tempo don't exist in an interactive toggle.** `Core`'s capture-cue mechanism needs *some* bar granularity to close a window on, but there's no musical tempo to tick against a keypress. Resolved by treating each render-loop iteration as one bar, with its nominal bpm computed from the *actual* elapsed time since the previous tick (not a fixed value) - `beats_per_bar=1` means seconds-per-bar equals that elapsed time exactly, which forces `core/timeline.py` to record a fresh, exactly-real-time breakpoint on every single tick rather than extrapolating from one fixed rate. That sidesteps the nominal-vs-actual drift the scripted driver's real-hardware run hit two entries up (there's no fixed nominal rate here to drift from) without touching `Timeline` itself.
2. **The single-managed-window design (v2.2, above) didn't have a "bring the preview back" story**, and restarting the tee'd preview after killing it was ruled out empirically-adjacent, not tried and failed: `RingCapture`'s preview slave carries `onfail=ignore`, and ffmpeg does not retry a dropped tee output once it fails - reopening a listener on the same port afterward would very likely never receive frames again. Resolved by never stopping the preview in the first place: it starts once and runs for the whole session; a *second*, single-slot window shows only the most recent capture's loop for a few seconds, then closes itself automatically, leaving the ever-present preview as what's on screen between takes. This is a considered reinterpretation of "contained to a single window" (your answer to the second clarifying question this pivot opened with) as "loops never pile up their own windows" rather than "preview and loop must literally share one process slot" - flagged here explicitly since it's a judgment call, not a literal reading.

**The wall rebuild: `loopwall play` becomes one browser window, a real growing grid (2026-07-17):** on your direction - "adjust to have the loop video and monitor share the same window... eventual goal is a grid of looping videos" plus "we'll outgrow [an ffmpeg-only stopgap] this session, let's just go ahead and implement the full plan" - `InteractiveDriver` (ffplay windows + a Rich terminal dashboard, two separate surfaces) is retired outright and replaced by `drivers/cli/wall.py`'s `WallDriver`: async, not a synchronous keypress-poll loop, because control now lives in the browser page itself rather than a terminal. `server/app.py` is a real FastAPI app now (`/console` is still the only stub left, `STUBS.md`) serving `wall/index.html` - vanilla HTML/CSS/JS, no build step, no framework, matching this project's own "no new dependency without a reason" discipline - polling `/wall/state` every 200ms and posting `/wall/control` on spacebar. Semantics changed too, not just surface: each new recording now allocates a *new* track (`WallDriver._next_track`) rather than re-recording track 1, so completed takes accumulate as permanent tiles instead of replacing each other - the grid PLAN.md §3.5 always described, a real ahead-of-schedule slice of it (`PLAN.md` §3.7 rewritten in place), not a mockup.

Live preview initially went through `server/mjpeg.py`'s `MjpegRelay` - a second ffmpeg process playing the same "viewer" role the retired ffplay window had, decoding the ring's tee'd h264 and re-encoding it as MJPEG for a plain `<img>` tag. Two real bugs surfaced testing this against real hardware, both fixed at the root:

1. **The grid rendered as vertical strips, not a square-ish grid.** CSS `grid-template-columns: repeat(auto-fit, minmax(240px, 1fr))` greedily packs as many min-width columns as fit per row - for a small tile count on a wide screen, that's just one row of narrow strips, not PLAN.md §3.5's own `packed` layout (`cols = ceil(sqrt(N))`). Fixed by computing that formula in JS (`layoutGrid()`) and setting `grid-template-columns`/`rows` explicitly instead of trusting `auto-fit`.
2. **Live-preview framerate degraded over a session.** Root cause: every track tile that entered "recording" state opened its *own* `<img src="/wall/preview.mjpg">` - a second, fully independent connection to the relay, duplicating the always-on "pending" tile's own stream - and when that tile later left the DOM (transitioning to its finished clip), nothing told the server the stream was unwanted; the streaming generator had no disconnect check and just ran forever. Every start/stop cycle left one more of these running. Fixed by construction, not by cleaning up harder: a track only ever becomes a tile once its clip exists (`WallDriver.toggle()`'s stop branch, not its start branch) - the pending tile alone covers "currently recording" - so there is only ever one live-preview connection, full stop; `request.is_disconnected()` checking was also added to the streaming generator as a backstop regardless.

**Ctrl-C not stopping the wall, on your report (2026-07-17):** root-caused by reading `uvicorn`'s own `server.py` directly rather than guessing: `Config.timeout_graceful_shutdown` defaults to `None`, and `Server.shutdown()` does `await asyncio.wait_for(self._wait_tasks_to_complete(), timeout=self.config.timeout_graceful_shutdown)` - with `None` that's an **unbounded** wait for every open connection to finish naturally. `/wall/preview.ts` is a deliberately-infinite MPEG-TS stream (server/app.py's own docstring already says as much) that only ends when its client disconnects - and the auto-opened browser tab keeps it open for exactly as long as the wall is on screen. **Three real bugs, found and fixed against real multi-camera + MIDI hardware (2026-08-09, on your report after hooking up a second camera and a MIDI device):** all three traced back, once investigated properly, to one shared root cause — `WallDriver`/`Core`'s synchronous extraction path (`Core`'s own docstring: "capture_cue completion is synchronous... x264 veryfast... well inside the plan's <=3s budget") never actually held at real capture resolution, and nothing downstream of it was built expecting that.

1. **"Second camera has trouble connecting."** Reproduced directly: the exact ffmpeg command `switch_camera()` builds for this machine's second real camera ("UHD 4K Camera") fails to open ("Could not run graph") - but `RingCapture.start()` only spawns ffmpeg and returns, never checking it actually started, so the *old* code swapped the broken ring in unconditionally and reported success. Fixed at the root: `capture/ring.py` gained `wait_until_ready()` (a bounded poll for a fast startup failure - confirmed empirically that a bad device exits well under a second, not a hang) and `tail_stderr()` (stderr now goes to a real file, not `DEVNULL`, specifically so a failure has something to show). `switch_camera()` now probes the requested device with a throwaway, non-tee'd `RingCapture` *before* touching the working one - deliberately not tee'd into the live preview relay during the probe, since `PreviewRelay._on_connect` accepts every inbound connection, and two ffmpeg processes racing to connect at once would interleave two MPEG-TS streams into one socket rather than just failing cleanly. The real mechanism, confirmed with a controllable artificial extraction delay standing in for the ~3.5s+ this session's own earlier hardware-gate work measured at real resolution: once a take is stopped, `WallDriver`'s control lock is held for the *entire* extraction, but the pending tile's own display already reads "ready - press space" the whole time - nothing on screen shows a take is still processing.
