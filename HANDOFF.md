Result: continuous ring capture + after-the-fact window extraction works — a requested 4.000s window came back as 3.900s (100 ms short), which touches the retrospective's falsifiable prediction #2 (`perspectives/2026-07-16-plan-retrospective.md`: "the ±1-frame duration assertion fails first on segment/GOP boundary rounding, not camera latency") — 100 ms is 3 frames at 30 fps, past the plan's ±1-frame target, and worth root-causing before the real `tests/integration/test_smoke.py` gate is written. Camera-safety note for future hardware work: `ffmpeg` on PATH here resolves to a Chocolatey launcher shim that spawns the real binary as a child process — killing only the tracked PID orphans a live capture with the camera still open (discovered the hard way, mid-session). `RingCapture.stop()` now kills the whole process tree (`taskkill /T` on Windows, `killpg` on POSIX), not just one PID; still not yet run against a `lavfi` synthetic source, which is what steps 6–7's own definition of done (ROADMAP.md) actually requires for the CI-facing path.

**Duration compensator, on your instruction (2026-07-16):** rather than root-causing the 100 ms gap now, `capture/extract.py` gained `DurationCompensator` — a session-scoped, explicitly-provisional rolling correction (no ADR; flagged for review/replacement once root-caused) that nudges a loop's requested end time by the previous loop's observed bias. `test_capture_poc.py` was rewritten to run it across two sequential real-webcam extractions and *measure*, not assert, whether it helps. It didn't converge: one real run showed no improvement at all (loop 2 still ~100 ms short despite asking for 100 ms more); a second showed a ~100 ms *overshoot* in the other direction. Together those rule out "fixed additive bias" as the model — something is quantizing the cut in a way that varies run to run, not a constant this stop-gap can be tuned against. Left in place as a real, working mechanism and an honest negative result, per your call to defer investigation rather than solve it now.

**CLI demo v2 (2026-07-16):** `loopwall demo` now starts a capture, the Tier 0 monitor display, *and* a live-preview window together, in one command. Space cuts everything since the last press into a clip that opens in its own looping window; the ring keeps recording underneath, uninterrupted, into what becomes the next one — verified for two sequential captures in one real session (below), not just one. Three real bugs surfaced building this, each with a permanent fix, not a workaround:

1. **Two processes can't open the same camera.** Confirmed empirically (a second `ffmpeg -f dshow` open on this dev machine's camera fails with an I/O error) before designing around it, not assumed. Live preview instead shares the ring's *one* capture process via FFmpeg's `tee` muxer — one encode, two sinks: the ring (unchanged) and `udp://127.0.0.1:<port>` as MPEG-TS, read by a persistent `ffplay`. `RingCapture` gained an optional `preview_udp_port` param, fully backward-compatible (all prior tests still pass unmodified).
2. **The tee muxer's bracketed option syntax breaks on Windows absolute paths** — `:` is tee's own option separator, colliding with a drive letter (`C:\...`); backslashes got silently mangled too. Root-caused with a minimal repro (confirmed: 0 ring segments, `[tee] No option found near "Users..."` in ffmpeg's own log once stderr wasn't suppressed) before fixing it — not patched blind. Fix: run ffmpeg with `cwd` set to the ring directory and use bare relative filenames inside the tee spec, sidestepping the escaping problem entirely rather than fighting tee's escaping rules.
3. **`lavfi` synthetic sources aren't real-time-paced by default** — ffmpeg processes them as fast as the CPU allows, so a test `RingCapture` reading "15s of content after a 4s sleep" is possible and did happen. Fixed with `-re` on the lavfi input (`monitor/camera.py`); existing lavfi-based tests' literal command-string assertions updated to match.

A fourth finding, caught before it became a bug rather than after: `ffplay.exe` on this machine is *also* a Chocolatey shim (confirmed by identical file size to `ffmpeg.exe`, 392704 bytes) — the same orphaned-child risk from the capture POC applies to the live-preview process too. Factored the process-tree-kill logic out of `RingCapture.stop()` into a shared `src/loopwall/proctree.py` (`kill_tree()`), used by both `RingCapture` and `demo.py`'s preview-process teardown, rather than duplicating or half-covering it. Also caught: Rich console markup treats `[space]`/`[q]` as (unrecognized) style tags and silently strips them — the controls line rendered with the labels missing entirely until switched to `(space)`/`(q)`.

**CLI demo v2.1, on your bug report "the camera isn't currently starting, the warm up never seems to open up a dummy video" (2026-07-17):** v2's UDP preview turned out to *never actually work* — every frame failed to decode ("non-existing PPS 0 referenced", "no frame!", on repeat, 100% reproducible against a real camera and against `lavfi`) — this is almost certainly what you hit. Root-caused rather than patched around: x264 sends its parameter sets once, at encode start (`-x264-params repeat-headers=1` was tried first and did *not* fix it - ruled out, not left in as a hopeful maybe); the actual cause is UDP packet loss/reordering, confirmed even on loopback. Switched the preview transport from UDP to TCP, which decoded perfectly (0 errors) the first time it was tried. That surfaced a second, worse issue: `ffmpeg ... ?listen=1` (server mode) blocked the *entire* tee output - ring included - until a viewer connected, confirmed with a minimal repro (ring segment stayed at 0 bytes while nothing was connected). Reversed it: `ffplay` listens, `RingCapture`'s ffmpeg connects out as the client (`preview_udp_port` renamed to `preview_tcp_port` throughout); the tee's preview slave also gained `onfail=ignore` plus a 3s bounded connect timeout, so a slow/absent/disconnected viewer costs only the preview, never the ring - demonstrated when `ffplay`'s bind failed outright on one verification run (Windows error -10013, didn't recur, likely transient) and the ring kept capturing both clips regardless. Last piece: a fixed 0.5s delay before starting the ring after spawning the preview wasn't remotely enough (measured `ffplay`'s real bind time at ~1.1s through its own shim, and a *failed* connection attempt turned out to stall the whole tee for ~5s more, per ffmpeg's own log - "Resumed reading... after a lag of 4.929s"), so `demo.py` gained `_wait_for_listening()`, polling the OS's own listening-socket table (`netstat`/`ss`) rather than guessing a delay or connecting a probe (which would consume the listener's one-shot accept and break the real connection after it). `run()` now owns `ring`'s full start/stop lifecycle itself (was: caller's `with ring:`) since the ordering - preview listening before ring starts - has to be guaranteed somewhere, and this is the only place that can. Verified end to end against real hardware afterward: real camera → live preview → space → loop → space again → second loop → 'q' → clean teardown, no decode errors, ~7s from ring start to first segment (camera's own startup latency plus the preview-readiness wait, not a stall - both already-known costs, just not previously measured together). Tests updated to use a real bound socket as the preview stand-in (`_FakeListener`, `tests/integration/test_demo_lifecycle.py`) rather than a bare mock, so they exercise the actual fast-path ordering instead of always hitting the 3s backstop.

New: `src/loopwall/keypress.py` (non-blocking single-key polling, stdlib `msvcrt`/`termios`+`select`, no new dependency — this is what lets the monitor's live display and the space control share one loop without the terminal contention a blocking `input()` prompt caused in v1). 8 tests (4 unit: render content, exact `ffplay` command args for both the preview and loop players including a regression check that `-loop 0` and `-autoexit` never appear together; 4 lavfi-based lifecycle, `poll_key`/`RawMode` monkeypatched rather than made `run()` parameters — they're an ambient input mechanism, and `RawMode` would otherwise try to manipulate a real tty that doesn't exist under pytest). Verified for real, end to end, twice in one session: real camera → live-preview window → space → looping clip window (905KB, ~15s) → space again 4s later → a second looping clip window (205KB, ~4s) → 'q' → `tasklist` confirmed the capture and live-preview processes both gone, while the two loop windows (by design) kept looping until manually closed.
