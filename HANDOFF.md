Three real bugs surfaced building this, each with a permanent fix, not a workaround:

1. **Two processes can't open the same camera.** Confirmed empirically (a second `ffmpeg -f dshow` open on this dev machine's camera fails with an I/O error) before designing around it, not assumed. Live preview instead shares the ring's *one* capture process via FFmpeg's `tee` muxer — one encode, two sinks: the ring (unchanged) and `udp://127.0.0.1:<port>` as MPEG-TS, read by a persistent `ffplay`. `RingCapture` gained an optional `preview_udp_port` param, fully backward-compatible (all prior tests still pass unmodified).
2. **The tee muxer's bracketed option syntax breaks on Windows absolute paths** — `:` is tee's own option separator, colliding with a drive letter (`C:\...`); backslashes got silently mangled too. Root-caused with a minimal repro (confirmed: 0 ring segments, `[tee] No option found near "Users..."` in ffmpeg's own log once stderr wasn't suppressed) before fixing it — not patched blind. Fix: run ffmpeg with `cwd` set to the ring directory and use bare relative filenames inside the tee spec, sidestepping the escaping problem entirely rather than fighting tee's escaping rules.
3. **`lavfi` synthetic sources aren't real-time-paced by default** — ffmpeg processes them as fast as the CPU allows, so a test `RingCapture` reading "15s of content after a 4s sleep" is possible and did happen. Fixed with `-re` on the lavfi input (`monitor/camera.py`); existing lavfi-based tests' literal command-string assertions updated to match.

A fourth finding, caught before it became a bug rather than after: `ffplay.exe` on this machine is *also* a Chocolatey shim (confirmed by identical file size to `ffmpeg.exe`, 392704 bytes) — the same orphaned-child risk from the capture POC applies to the live-preview process too. 1. **Bar/tempo don't exist in an interactive toggle.** `Core`'s capture-cue mechanism needs *some* bar granularity to close a window on, but there's no musical tempo to tick against a keypress. Live preview initially went through `server/mjpeg.py`'s `MjpegRelay` - a second ffmpeg process playing the same "viewer" role the retired ffplay window had, decoding the ring's tee'd h264 and re-encoding it as MJPEG for a plain `<img>` tag. Two real bugs surfaced testing this against real hardware, both fixed at the root:

1. **The grid rendered as vertical strips, not a square-ish grid.** CSS `grid-template-columns: repeat(auto-fit, minmax(240px, 1fr))` greedily packs as many min-width columns as fit per row - for a small tile count on a wide screen, that's just one row of narrow strips, not PLAN.md §3.5's own `packed` layout (`cols = ceil(sqrt(N))`). Fixed by computing that formula in JS (`layoutGrid()`) and setting `grid-template-columns`/`rows` explicitly instead of trusting `auto-fit`.
2. **Live-preview framerate degraded over a session.** Root cause: every track tile that entered "recording" state opened its *own* `<img src="/wall/preview.mjpg">` - a second, fully independent connection to the relay, duplicating the always-on "pending" tile's own stream - and when that tile later left the DOM (transitioning to its finished clip), nothing told the server the stream was unwanted; the streaming generator had no disconnect check and just ran forever. Every start/stop cycle left one more of these running. Fixed by construction, not by cleaning up harder: a track only ever becomes a tile once its clip exists (`WallDriver.toggle()`'s stop branch, not its start branch) - the pending tile alone covers "currently recording" - so there is only ever one live-preview connection, full stop; `request.is_disconnected()` checking was also added to the streaming generator as a backstop regardless.

**Live-preview latency rework, on your report it was "almost not usable" (2026-07-17):** asked for a review before acting - traced the full pipeline and found two real, independent, additive latency sources, not one, both addressed rather than picking the easier one:

1. **`RingCapture`'s shared h264 encoder had no low-latency tuning.** Without `-tune zerolatency`, libx264 defaults to B-frames and a lookahead buffer (tens of frames) that optimizes compression at the cost of holding output back internally - on its own, plausibly several hundred ms to over a second at 30fps. Since the ring's encode is shared between the archival segments and the tee'd preview (deliberately, to avoid a second redundant encode), this affected both. Fixed with a one-line addition to `capture/ring.py`'s `encoder_extra_args`; the compression-efficiency cost lands only on the ring's own short-lived, auto-deleted segments, since a captured clip gets its own separate, quality-focused re-encode at extraction time regardless (`capture/extract.py`).
2. **The MJPEG relay did a full decode-then-re-encode round trip on top of that.** On your call to go straight to the bigger rework rather than measure the tuning fix in isolation first: `server/mjpeg.py`'s `MjpegRelay` (a second ffmpeg process) is gone, replaced by `server/relay.py`'s `PreviewRelay` - a plain asyncio TCP server, no ffmpeg at all, that forwards the ring's raw h264/MPEG-TS bytes to subscribers untouched. The browser now decodes them itself via `mpegts.js` (vendored into `wall/mpegts.js`, not CDN-loaded - a live-performance tool can't depend on internet reachability at showtime; Apache-2.0, fetched once from jsdelivr's npm mirror, v1.8.0), configured with `enableStashBuffer: false` and `liveBufferLatencyChasing: true` so the player itself doesn't quietly re-add the buffering that was just removed server-side.
